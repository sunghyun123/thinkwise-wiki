## 2026-08-18 — 개인용 MVP를 사내 상시 서비스로 전환

개인 PC에서 혼자 쓰던 검색 앱을 사내 서버 PC에서 24시간 돌리고, 사내 다른 PC에서 접속할 수 있게 했다.

### 최종 상태

| 항목 | 값 |
| --- | --- |
| 사내 접속 주소 | <http://DESKTOP-318VJ68:8000> (예비: `192.168.0.76:8000`) |
| 설치 위치 | `C:\apps\thinkwise-wiki` |
| 실행 방식 | 작업 스케줄러 `ThinkwiseWiki` — SYSTEM 계정, 부팅 시 시작, 시간 제한 없음 |
| 방화벽 | `Thinkwise Wiki 8000` — TCP 8000 인바운드, Private/Domain, `192.168.0.0/24`만 |
| 로그 | `C:\apps\thinkwise-wiki\logs\server.log` (읽을 때 `-Encoding UTF8`) |
| DB 계정 | `tw_ro` — 두 테이블 `SELECT`만 |
| 로그인 | **없음** |

관련 커밋: `40ed0a6`(서버 경로 분리) → `8ce9c3e`(기동 실패 수정) → `bdad922`(인코딩 수정) → `45d8f2d`(접속 주소 안내).

### 서버 여력 점검 (배포 전)

씽크와이즈와 NAS가 이미 도는 PC라 자리가 있는지 먼저 확인했다.

- RAM 15.8GB 중 6.6GB 여유, **커밋 차지 11.1/17.3GB** — 스왑 압박 없음(이 숫자가 실제 판단 근거)
- CPU 부하 9% (Pentium G7400, 2코어)
- 8000번 포트 비어 있음, C: 128GB 여유

메모리 상위 목록에 씽크와이즈도 NAS도 안 보였고 제일 무거운 건 Edge(3개 합쳐 885MB)였다.
uvicorn 하나(70~120MB)는 Edge 탭 하나보다 가볍다고 판단해 진행했다.
**코어가 2개뿐이라 `--workers`는 늘리지 않았다.**

### 겪은 문제 3건

**1. `.ps1` 실행이 막힘 (`UnauthorizedAccess`)**

윈도우가 직접 만든 스크립트 파일의 실행을 기본 차단한다.
`PowerShell -ExecutionPolicy Bypass -File .\스크립트.ps1` 형태로 **이번 실행에만** 예외를 뒀다.
`Set-ExecutionPolicy`로 정책 자체를 풀지는 않았다 — 씽크와이즈와 NAS가 도는 PC의 전역 보안 설정을
이 앱 하나 때문에 낮출 이유가 없다.

**2. 서버가 뜨자마자 죽음** (수정: `8ce9c3e`)

`run_server.ps1` 첫머리의 `$ErrorActionPreference = "Stop"`이 원인이었다.
uvicorn은 `INFO: Started server process` 같은 **정상 로그도 표준 오류(stderr)로 내보내는데**,
파워셸은 외부 프로그램이 stderr에 쓰면 그것을 오류로 포장한다.
`Stop`이 그 포장을 중단 사유로 삼아서 **"서버가 시작됐습니다"라는 성공 알림이 서버를 죽였다.**

수정은 설치 검사(`.venv`·`.env` 존재를 보는 `throw` 두 줄)가 끝난 **뒤에** `Continue`로 되돌리는 것.
검사가 위쪽에 있고 `throw`는 이 설정과 무관하게 중단시키므로, **설정 실수는 여전히 시끄럽게 죽고
정상 로그만 조용히 지나간다.** 로그에 남길 때는 `"$_"`로 오류 포장을 벗겨 원래 한 줄만 남긴다.

**3. 로그의 한글이 `?쒖옉`으로 깨짐** (수정: `bdad922`)

처음엔 파이썬 출력 인코딩(`PYTHONIOENCODING`)을 의심했는데 틀렸다.
진짜 원인은 **스크립트 파일 자체**였다 — 윈도우 PowerShell 5.1은 `.ps1`을 열 때 파일 맨 앞
3바이트 표식(BOM)이 없으면 UTF-8이 아니라 시스템 기본 글자표(cp949)로 읽는다.
그래서 스크립트 안의 한글이 **파싱 시점에 이미 깨진 채로** 변수에 들어갔고,
그 깨진 글자가 로그에 *정확하게* 저장됐다. 읽을 때 `-Encoding UTF8`을 붙여도 안 고쳐지던 이유다.

`.ps1` 세 개를 BOM 붙여 다시 저장해 해결했다.
**실질 피해는 로그 헤더가 아니라 `throw` 메시지였다** — `.venv`가 없을 때 뜨는 안내가
전부 깨진 채로 나오게 돼 있었다. 평소엔 안 보이다가 사고 났을 때만 드러나는 자리에 있던 병이다.

### 결정과 이유

**설치 위치를 `C:\apps`로.** 작업 스케줄러가 SYSTEM 계정으로 실행하는데 `C:\Users\...` 아래에 두면
권한이 얽히기 쉽다. (실제로는 SYSTEM이 사용자 폴더의 파이썬을 문제없이 읽었지만, 여지를 남길 이유가 없다.)

**개인용/서버용 실행 파일을 분리.** `run_local.ps1`은 `127.0.0.1`, `run_server.ps1`은 `0.0.0.0`.
한 파일에 옵션으로 두면 개인 PC에서 무심코 사내에 열리는 사고가 난다.

**IP를 고정하지 않고 컴퓨터 이름으로 안내.** 서버 IP가 공유기 자동 할당(DHCP)이라 언젠가 바뀔 수 있다.
공유기에 고정 예약을 넣는 방법도 있었지만, 일부 공유기는 설정 저장 시 재시작해서 **사내망 전체가
잠깐 끊긴다.** `DESKTOP-318VJ68:8000`이 실제로 되는 걸 확인했고, 이러면 IP가 바뀌어도 링크가 따라가고
공유기를 한 글자도 안 건드린다. 윈도우 PC끼리 이름을 찾는 기능에 기대므로 100%는 아니다 —
안 되는 PC가 나오면 그 PC에만 IP를 알려주면 된다.

**로그인은 보류.** 본인 판단으로 미뤘다. 현재 접근 제한은 방화벽의 대역 제한뿐이다.

### 검증한 것 / 안 한 것

확인함 — 다른 PC에서 검색 성공, 방화벽 통과, 이름 접속, 서버 프로세스 상시 대기,
씽크와이즈 관련 기존 작업을 덮어쓰지 않음(`ThinkwiseWiki` 외에 같은 이름 없음).

**확인 안 함** — ①**재부팅 후 자동 시작.** 등록만 확인했고 실제로 재부팅해보지는 않았다.
씽크와이즈가 도는 서버라 확인 목적으로 재부팅하지 않았고, 다음 재부팅 때 보기로 했다.
②**여러 명 동시 검색 시 DB 부하.** 지금까지 검색은 전부 한 명이었다.

### 남은 일

1. **공지는 단계적으로.** 이 앱은 씽크와이즈와 같은 MySQL에 붙고, 검색이 `LIKE '%검색어%'`라
   테이블을 통째로 훑을 수 있다. 여러 명이 동시에 검색하면 **씽크와이즈 본체가 느려진다.**
   소수에게 먼저 열어 며칠 관찰하고, 이상 없으면 전체 공지한다.
   문제가 생기면 `Stop-ScheduledTask -TaskName ThinkwiseWiki` 한 줄로 내린다.
   (데이터가 망가질 위험은 없다 — `tw_ro`는 `SELECT`만 가능하다.)
2. **로그인 붙이기.** 사람이 늘기 전에.
3. 검색이 느려지면 읽기 복제본이나 별도 검색 인덱스 검토.

## 2026-08-18 (2) — 검색을 운영 DB에서 떼어내 로컬 색인으로

위 기록의 남은 일 3번을 앞당겨 처리했다. "느려지면 검토한다"였는데, 재보니 **이미 느렸다.**

### 왜 지금 했나

세 가지 불만에서 출발했다. ①기술적으로 얕다 ②같은 내용이 4~5줄씩 반복된다
③상위 50건만 나와서 과거를 못 찾는다. 재보니 **②와 ③은 한 문제**였고,
③은 성능 문제가 아니었다.

실측으로 드러난 것:

- `work_log`에는 **`c_date` 인덱스조차 없다.** 유일한 인덱스가 PK 하나뿐이라
  `EXPLAIN`이 `type=ALL, rows=407023, Using temporary; Using filesort` — 검색 한 번이
  53만행 전체 스캔 + 전체 정렬이었다. 검색 1회 663ms.
- **`LIMIT`은 이 비용에 들어가지 않는다.** 100건이든 1000건이든 스캔·정렬은 똑같이 한다
  (663ms → 714ms). 즉 과거가 안 보이던 건 성능 때문이 아니라 그냥 버리고 있었기 때문이다.
- 그래서 `'공사'` 검색이 **6년치 중 최근 5일만** 보여주고 있었다(51,181건 매칭 중 100건).
  흔한 업무 단어일수록 과거가 통째로 사라진다.

### 최종 상태

| 항목 | 값 |
| --- | --- |
| 검색 경로 | 운영 MariaDB → **로컬 SQLite 색인**(`data\wiki_index.db`, 약 105MB) |
| 동기화 | 작업 스케줄러 `ThinkwiseWikiSync` — 10분마다 + 부팅 시, SYSTEM 계정 |
| 동기화 방식 | `WHERE indx > 커서` 증분. PK 범위 스캔이라 기존 검색 1회보다 가볍다 |
| `'공사'` 검색 | 663ms → **304ms**, 운영 DB 접촉 **0회** |
| 100건 → 1000건 | +14ms (사실상 무료) |
| 결과 단위 | 이벤트 51,182행 → **가지 25,258개** |
| 로그 | `logs\sync.log` (읽을 때 `-Encoding UTF8`) |

관련 커밋: `1f63438`(본체) → `31a09fa`(작업 등록 수정).

### 겪은 문제 3건

**1. 분석 중에 운영 DB를 159초 점유했다**

MOVE/DEL 쌍을 세려고 인덱스 없는 컬럼으로 셀프 조인을 걸었다(35,197 × 539,205).
클라이언트가 타임아웃된 뒤에도 서버에서 계속 돌아서 `KILL QUERY`로 중단시켰다.
같은 질문을 **PK(`indx`)를 타는 조인**으로 바꾸니 0.1초에 끝났다.
운영 DB를 조심하자고 문서에 써놓고 조사하다가 그걸 어긴 셈이다.

**2. 서버가 `sync_index.ps1`을 못 찾음**

작업 브랜치를 푸시하지 않은 채로 서버에서 `git pull`을 해서 파일 자체가 없었다.
`-File` 매개 변수 오류로 나타나 스크립트 문제처럼 보였지만 원인은 배포 순서였다.

**3. 동기화 작업 등록이 거부됨** (수정: `31a09fa`)

```
Register-ScheduledTask : 작업 XML에 형식이 잘못되었거나 범위를 벗어난 값이 있습니다.
(8,42):Duration:P99999999DT23H59M59S
```

"무기한 반복"을 만들려고 `RepetitionDuration`에 `[TimeSpan]::MaxValue`를 넣은 게 원인.
그 값이 `P99999999DT23H59M59S`가 되는데 작업 스케줄러가 범위 밖으로 보고 등록을 거부한다.
**반복 기간을 아예 주지 않는 것이 옳다** — 비워 두면 무기한으로 읽는다
(확인: `Interval='PT10M' Duration=''`). 검증 없이 쓴 관용구였다.

### 결정과 이유

**SQLite FTS5를 붙이려다 재보고 뺐다.** trigram 토크나이저는 3글자 이상만 처리해서
`공사·설계·견적·도면` 같은 **2글자 검색이 전부 0건**이 된다. 우리 검색어는 대부분 2글자다.
반면 로컬에서는 평범한 `LIKE` 전체 스캔이 25~300ms라 색인 기술이 애초에 필요 없었다.
문제를 푼 건 색인 자료구조가 아니라 **데이터를 운영 DB 밖으로 꺼낸 것 자체**다.

**접기를 저장하지 않고 검색할 때 계산한다.** 저장하면 새 이벤트마다 요약을 갱신해야 하고
갱신 경로를 하나만 빠뜨려도 영구히 어긋난다. 파생시켜 두니 펼치기가 `GROUP BY`만 뺀
같은 쿼리 한 방이 됐고, 접기 규칙을 바꿔도 53만행 재적재가 필요 없다.

**삭제된 가지를 감추지 않고 `삭제됨`으로 표시한다.** 위키의 목적이 "예전에 그게 뭐였나"를
찾는 것이라 감추면 도구가 반쪽이 된다. 단 씽크와이즈는 가지를 옮길 때 `MOVE` 뒤에 `DEL`을
함께 남기는데(전체 MOVE의 88%, 31,055건), 이걸 삭제로 세면 **멀쩡한 가지 18,197개에
'삭제됨'이 붙는다.** 적재할 때 표시해 두고 판정에서 뺀다.

**`indx`를 증분 커서로 쓴다.** 근거는 53만행에서 `indx` 순서와 `c_date` 순서의
**역전이 0건**이라는 실측. PK라 범위 스캔이 매우 싸다.

**웹 서버와 동기화를 별도 작업으로 나눴다.** 동기화가 실패해도 검색은 계속 되어야 한다.
한 프로세스에 묶으면 한쪽 사고가 다른 쪽을 끌고 내려간다.

**색인 나이를 화면에 상시 표시한다.** 동기화가 죽어도 검색은 되기 때문에, 결과만 봐서는
낡은 걸 알 수 없다. 어제 만든 가지는 "낡아 보이는" 게 아니라 **아예 없는 것처럼 보인다**
(결과 0건 = "정말 없다"와 구분 불가). 그래서 결과가 아니라 별도 배지로 알린다.

### 검증한 것 / 안 한 것

확인함 — 53만행 적재 20초, `gubun` 분포와 MOVE 짝 개수(31,055)가 운영과 정확히 일치,
증분 동기화가 새 24행만 가져옴, 자동 테스트 22개 통과, 실데이터로 화면(접기·삭제 배지·
필터·펼치기) 확인, 배포 후 사내에서 검색 성공, 색인 배지 정상(초록 "7분 전 갱신"),
`ThinkwiseWiki`·`ThinkwiseWikiSync` **두 작업 모두 등록·실행 확인**.

**확인 안 함** — ①**재부팅 후 자동 시작**(웹·동기화 둘 다). 여전히 등록만 확인한 상태다.
씽크와이즈가 도는 서버라 확인 목적으로 재부팅하지 않았고, 다음 재부팅 때 본다.
②**과거 행이 수정·삭제되는 경우.** 증분 커서는 `indx`가 커지는 것만 본다. 감사 로그라
그럴 일이 없어 보이지만 확인한 사실은 아니다. 이상하면 `sync_index.ps1 -Full`로 다시 만든다.
③**여러 명 동시 검색.** 이제 검색이 운영 DB를 안 거치므로 위험은 크게 줄었지만,
2코어 PC에서 로컬 색인 스캔(최대 300ms)이 여러 개 겹칠 때는 아직 안 봤다.

### 남은 일

1. **로그인.** 순위가 더 올라갔다. 검색이 빨라지고 6년치 과거까지 닿게 되면서
   "URL만 알면 전 직원 작업 이력을 훑을 수 있다"의 무게가 커졌다. 공지를 넓히기 전에 붙인다.
2. **필터가 주소에 안 남는다.** 새로고침하면 초기화되고 검색 결과 링크를 남에게 못 보낸다.
3. 정렬은 최신순 고정. 관련도 순은 넣지 않았다 — 순서 기준이 눈에 안 보이면 사용자가 왜 이

## 2026-08-18 (3) — 삭제된 가지를 검색에서 감춤

### 왜 뒤집었나

같은 날 (2)에서 **"삭제된 가지를 감추지 않고 `삭제됨`으로 표시한다"**고 적었다. 써보니
그 판단이 틀렸다. 이 도구는 남이 쓴 것까지 전부 조회되는데, 잘못 써서 지운 것이나
남에게 보이기 싫어 지운 것까지 계속 나오면 **지우는 행위 자체가 아무 효과가 없다.**
그러면 사람들이 마음 놓고 쓰지 않는다. "예전에 그게 뭐였나"를 찾는 이득보다
"지운 게 안 지워진다"는 손해가 크다고 보고 정책을 바꿨다.

### 결정과 이유

**내보내는 지점에서만 가린다(색인에는 원본을 남긴다).** 동기화 때 아예 안 담는 방법도
있었지만 삭제 판정은 **나중에 바뀌는 성질**이다(오늘 살아 있던 가지가 내일 지워진다).
그러면 증분 동기화에 "지난 것 청소" 단계를 새로 붙여야 하고, 그 단계가 조용히 실패하면
**프라이버시가 조용히 새는 쪽으로** 고장난다. 내보내는 곳에서 가리면 정책을 되돌릴 때
53만행 재적재도 필요 없다.

**조건을 문자열 하나(`NOT_DELETED`)로 뽑아 두 경로에 끼웠다.** 삭제된 가지가 화면까지
나갈 수 있는 길은 검색 목록과 **펼치기 API 두 개**다. 목록에서만 가리면 `/api/branch/{id}`에
숫자를 넣어 그대로 볼 수 있다. 둘이 각자 판정하게 두면 한쪽만 고쳐졌을 때 새는데,
새는 방향이 조용해서 눈에 안 띈다. 목록 쪽은 접기 결과를 담는 임시 테이블을 만들 때
걸러서 **목록·전체 개수·패싯 셋이 구조적으로 같은 기준**을 쓰게 했다.

**판정 근거가 없으면(NULL) 숨기는 쪽에 넣었다.** 잘못 숨기면 다시 보여주면 되지만
잘못 보여준 것은 되돌릴 수 없다. 실측으로 이 경우는 0건(가지 286,538개 중)이다.

**삭제된 가지와 없는 가지에 같은 404, 같은 문구를 준다.** "삭제된 가지입니다"라고 답하면
지웠다는 사실 자체가 새고, 그게 숨기려던 것의 일부다.

**가려진 개수는 알리지 않는다.** "이 검색어에 지워진 게 2,120개 있다"는 말도 새는 것이다.
대신 규칙은 화면에 상시 적어 둔다("삭제된 가지는 검색되지 않습니다") — 규칙을 안 알리면
삭제가 실제로 효과가 있는지 모른 채로 쓰게 된다.

### 검증한 것 / 안 한 것

확인함 — 자동 테스트 24개 통과(삭제된 가지가 목록·개수·패싯·펼치기에서 전부 빠지는지,

(2,120개 = 8.4% 가려짐), 실제로 지워진 가지 `indx 248665`가 목록에 없고 펼치기가 빈 응답,
살아 있는 가지는 정상 펼침, 검색 속도 322ms(이전 307ms — `WHERE` 한 줄은 접기 비용에 묻힌다).

**확인 안 함 / 못 고침** — **제목이 바뀐 뒤 지워진 가지.** 가지의 신원이 (맵 + 제목)뿐이라
이름을 A→B로 바꾸고 지우면 `DEL`은 B에만 찍히고, **A로 접힌 줄은 계속 검색된다.**
`work_log`에 가지 고유 id가 없어 A와 B를 연결할 수 없다 — 연결을 못 하니 **규모도 셀 수 없다**
(EDIT 이벤트가 82,276건이라 이름 변경 자체는 드물지 않다). 그래서 이 기능은
"삭제하면 완전히 지워진다"가 아니라 **"현재 제목으로는 검색되지 않는다"**가 정확한 설명이다.
운영 `work_log`에 가지 id 컬럼이 있는지는 아직 확인하지 않았다(있으면 이 한계가 풀린다).

### 진단에서 세 번 틀렸다

**1. "http라서 링크가 안 걸린다"가 아니었다.** 스킴이 아니라 **점과 최상위도메인의 부재**가 원인이었다.
`DESKTOP-318VJ68`은 윈도우 컴퓨터 이름이라 메신저 눈에 주소로 안 보인다. 검증은 5초 걸렸다 —

나란히 보내니 원인이 확정됐다. **접속되는지가 아니라 파랗게 변하는지만 보면 되는 테스트였다.**

**2. 포트 80으로 내리려다 씽크와이즈를 멈출 뻔했다.** 주소에서 `:8000`을 없애려고 80번으로

**3. `wiki.yjsboard.com`을 만들었는데 쓸 수 없었다.** A 레코드도 정상이고 DNS 해석도 정상이었다

http 요청이 네트워크에 아예 나가지 않으므로 서버 로그에도 안 남는다.

우회는 불가능했다. 브라우저 캐시를 지워도 ERP를 한 번 열면 되살아나고, ERP에서
`includeSubDomains`를 떼도 이미 나간 지시가 각 직원 브라우저에 1년치 남아 있다.
**`yjsboard.com` 아래로는 http를 쓸 수 없다.**

### 결정과 이유

**도메인을 `yjselect.com`으로 바꿨다.** 회사가 가진 다른 도메인인데, 같은 HSTS 헤더를 보내되
`includeSubDomains`가 없다 — 그래서 도메인 자신만 https로 묶이고 서브도메인은 자유다.
**헤더 한 조각의 유무가 쓸 수 있는 도메인과 없는 도메인을 갈랐다.**

**포트 8000을 그대로 뒀다.** 80번은 씽크와이즈 것이라 못 쓴다. IIS에 호스트 헤더로 위키용 사이트를
추가해 8000으로 넘기는 방법도 있었지만, **회사 기간계 시스템이 도는 IIS에 모듈(URL Rewrite·ARR)을
설치**해야 해서 접었다. 임시 위키 하나 때문에 씽크와이즈 웹서버를 건드릴 이유가 없다.
카톡이 포트 붙은 주소도 링크로 잡는다는 것은 위 1번 테스트에서 이미 확인했다.

**https는 안 붙였다.** 사설 IP를 가리키는 도메인이라 인증서 발급에 DNS 챌린지가 필요하고,
자동 갱신을 붙이지 않으면 **90일마다 손으로 갱신**해야 한다. 잊는 날 위키가 죽는다.
이 위키는 나중에 만들 씽크와이즈+NAS MCP 모델로 대체될 임시 시스템이라 그 유지비를 달지 않기로 했다.
대가는 주소창의 "안전하지 않음" 표시와, **주소를 손으로 칠 때 `https`를 쓰면 실패**한다는 것이다.

**IP를 고정하지 않았다.** A 레코드는 `192.168.0.76`을 손으로 적어 넣은 것이라 IP가 바뀌면 도메인이 죽는다.
8/18에 공유기 순단을 피하려고 IP 고정을 안 한 결정이 여기서 대가를 치르는 셈인데,
**컴퓨터 이름 주소를 없애지 않고 남겨둔 것**으로 덮었다. 그래서 진단이 한 줄로 끝난다 —
**컴퓨터 이름으로는 되는데 도메인으로 안 되면 IP가 바뀐 것**, `yjselect.com` DNS에서
`wiki` A 레코드 값만 고치면 복구된다.

### 이번에 얻은 것 — 실패가 다른 시스템의 성공으로 위장한다

지금 주소는 세 부분(`http` / `wiki.yjselect.com` / `:8000`)이 다 맞아야 하는데,

**회사에서 실제로 쓰는 다른 시스템의 로그인 화면이 정상적으로 떴다.**
`wiki.yjselect.com`이라는 이름이 위키와 씽크와이즈 둘을 동시에 가리키고,
둘을 가르는 것은 주소 끝의 다섯 글자뿐이다.

없앨 수 없다(80번은 씽크와이즈 것이고 IIS 프록시는 비용으로 접었다). 그래서 처방은

## 2026-08-20 — 액세스 로그를 직접 남기기 (사용 기록으로 읽히게)

"이 위키의 실시간 사용 로그를 보고 싶다"에서 시작했다. 로그는 있었는데 쓸 수가 없었다.

### 배경 — 로그가 있는데 못 읽는 상태였다

uvicorn 기본 액세스 로그는 이렇게 생겼다.

```
INFO:     192.168.0.22:65390 - "GET /api/search?q=%EA%B0%90%EB%A6%AC&limit=100 HTTP/1.1" 200 OK
```

**시각이 없고 검색어가 `%`인코딩이다.** 그래서 306줄을 다 긁어 봐도 "언제"를 복원할 수 없고
검색어도 사람이 못 읽는다. 시각이 붙는 줄은 `run_server.ps1`이 찍는 `=== 시작: ... ===` 뿐이다.

로그를 디코딩해서 세어 본 결과가 이 작업을 하게 만든 이유였다 — 306줄 중 본인(개발 PC 170,
서버 자신 44)을 빼면 **다른 PC 세 대의 24건**이 전부였고, 그 24건은 검색 → 결과 펼치기까지
갔다. 즉 쓰이고는 있는데 얼마나 쓰이는지를 셀 수단이 없었다.

### 결정 — 우리가 직접 남긴다 (기각한 두 안)

- **A안: uvicorn 로그 설정 파일(`--log-config`)에 `%(asctime)s`만 추가.** 앱 코드는 안 건드린다.
  기각 이유: uvicorn 내부 설정을 우리 저장소에 복사해 두는 것이라 uvicorn을 올리는 날
  사본이 조용히 낡는다. 그리고 **검색어가 여전히 `%`인코딩이라 목적을 못 이룬다.**
- **C안: 앱이 뜰 때 `uvicorn.access` 로거의 포맷터를 코드로 갈아끼운다.** 파일도 스크립트도
  안 건드려서 가장 싸다. 기각 이유: "uvicorn이 로깅을 먼저 설정하고 그 다음에 앱을 import한다"는
  **순서에 기대는 것**이고, 그 순서가 바뀌면 에러 없이 그냥 타임스탬프가 안 붙는다.
- **B안(채택): 미들웨어로 직접 남기고 uvicorn 액세스 로그는 끈다.** 고른 이유는
  "검색어까지 읽혀야 사용 로그로 쓸모가 있다" — 시각만 붙이는 A·C안은 목적의 절반만 준다.

```
[2026-08-20 11:39:48] 192.168.0.78 GET /api/search?q=오늘 한일&limit=10 200 118ms
```

구현에서 걸린 것 네 개.

1. **`logger.info`가 그냥 사라진다.** uvicorn은 `uvicorn.*` 로거만 설정하고 root는 안 건드리므로,
   핸들러를 손수 붙이지 않으면 우리 `info`는 어디에도 안 나온다(에러도 안 난다).
2. **`print`를 쓰면 로그 실패가 검색 실패로 둔갑한다.** `run_local.ps1`은 `PYTHONIOENCODING`을
   세팅하지 않아서, 한글 검색어를 `print`하면 콘솔 인코딩에서 터지고 그 예외가 미들웨어를
   통과해 **요청이 500이 된다.** `logging`은 핸들러에서 난 예외를 삼키므로 그 둔갑이 없다.
   (yjs_ai_manager에서 `print` 한 줄이 성공한 AI 호출을 실패로 만든 사고와 같은 계열.)
3. **로그 위조.** 검색어는 사용자가 보낸 문자열이라 `%0A` 하나로 가짜 줄을 끼워 넣을 수 있다.
   로그는 나중에 사람이 읽고 판단하는 근거라서, 출력할 수 없는 글자는 공백으로 바꾼다.
4. **경로와 쿼리를 나눠 디코딩한다.** 화면이 `URLSearchParams`로 주소를 만들어 공백이 `+`로
   오므로("오늘 한일" → "오늘+한일") 쿼리 쪽만 그 규칙으로 풀어야 한다. 경로의 `+`는 글자다.

미들웨어는 보안 헤더 미들웨어보다 **아래**에 선언했다. starlette의 `add_middleware`가
`insert(0, ...)`이라 나중에 선언한 것이 바깥이 되고, 바깥이어야 소요 시간 전체와
최종 상태코드를 본다.

### 검증한 것 / 안 한 것

확인함 — 테스트 27개 통과(포맷·실패 요청도 남는지·줄바꿈 위조 방지 3건 추가),
